# EasyDOC 프롬프트 설계 문서

> 교수 코멘트 대응: "졸업작품 내 주요부분, 단어교체 기준이 무엇인지 설명이 부족함"
>
> 본 문서는 `EasyDOC-frontend/easydoc-parser/main.py` 가 Gemini API에 전달하는 프롬프트의 **설계 의도와 기준**을 정리한다. 특히 단어 교체(쉬운말 변환)의 **선정 기준**과 **교체 원칙**을 중점적으로 설명한다.

---

## 1. 대상 독자 정의 (Why first)

EasyDOC의 모든 프롬프트는 **단 하나의 독자 집단**을 기준으로 작성된다.

- **연령**: 만 19~34세
- **특성**: 사회초년생 및 청년층
- **문해력 상태**: 일상 대화·생활에는 문제가 없으나, **설명서·계약서·안내문·법령** 등 **한자식 표현과 전문용어**가 섞인 문서를 읽을 때 이해에 어려움을 겪는 집단

### 근거 (중간발표 자료 기반)

1. **청년층 문해력 인식 설문**: "어떤 이유로 청년층의 문해력 저하 문제가 심각하다고 생각하십니까?" 중
   - **설명서·계약서·안내문·법령 등을 읽은 후 이해가 어려움: 45.7%** ← EasyDOC 타깃 영역과 정확히 일치
   - 어휘력 저하가 곧 문해력 저하로 이어짐: 55.3%
2. **2019 국민법의식조사 (한국법제연구원)**: 응답자 10명 중 7명이 법률 용어(76.3%)·법률 문장(78.4%)을 "이해하기 어렵다"고 응답.

즉, EasyDOC은 "일반 대중을 위한 쉬운말 도구"가 아니라 **"청년층이 계약·행정 문서에서 불이익을 당하지 않도록 돕는 도구"** 로 초점이 좁혀져 있다. 이 타기팅이 프롬프트 설계 전체의 출발점이다.

## 3. 단어 교체 기준 (핵심)

### 3.1 설계 원칙: "단일 기준"

이전 설계에서는 단어에 1~4단계 난이도를 매겼으나, **현재는 난이도 구분을 제거**하고 **단일 선정 기준**으로 통일했다.

**제거한 이유:**

1. 난이도는 모델이 스스로 4단계로 일관성 있게 판정하기 어려웠다 (같은 단어가 호출마다 다른 단계로 분류되는 "판정 흔들림"이 빈번).
2. 타깃 독자가 "청년층"으로 고정되면, 교체 여부는 **이 독자가 걸리느냐 안 걸리느냐**의 이진 판정이면 충분하다. 4단계는 오히려 UI·UX를 복잡하게 만들고 실제 사용 가치가 적었다.
3. 중간발표 이후 타깃이 "일반 대중" → "사회초년생·청년층"으로 좁혀지면서, 난이도 대신 **"청년 독자 기준 걸림 여부"** 라는 더 구체적이고 검증 가능한 단일 기준이 성립했다.

### 3.2 선정 기준 (현재 프롬프트)

청년 독자가 읽었을 때 **이해에 걸림이 될 만한 용어**를 모두 포함한다. 구체적으로:

- **일상 대화에서 거의 쓰지 않는 한자어·법률용어·행정 전문용어**
- **뜻은 알아도 문맥상 의미가 헷갈리는 표현**
  예: "준용", "기부채납", "상당한", "해당", "중도 해지 수수료"
- **제외 대상**:
  - 이미 쉬운 단어 (신청, 제출, 확인 등)
  - 한 글자 단어 ("법", "등" 등 문맥 없이 의미가 고정되지 않는 1음절어)

### 3.3 쉬운말 설명 톤 (교체 규칙)

프롬프트 예시에 못 박아둔 변환 톤:

```
기부채납|||개인이 가진 땅이나 건물을 나라·지자체에 공짜로 넘기는 것을 말해요.
준용|||다른 규정을 그대로 가져다 똑같이 적용한다는 뜻이에요.
중도 해지 수수료|||계약을 중간에 끊을 때 내야 하는 위약금이에요.
사업타당성|||사업을 해서 이득이 될지 미리 따져보는 검토를 말해요.
```

적용된 쉬운말 변환 기준:

- **한자어 → 순우리말 치환**: "기부채납" → "공짜로 넘기는 것"
- **수동태·법률투 제거**: "~에 귀속된다" → "~에게 넘긴다"
- **구어체 어미 사용**: "~이다/한다" → "~예요/~거예요"
- **구체화**: 추상 명사는 **무엇을 어떻게 하는지**로 풀어냄 ("사업타당성" → "이득이 될지 따져보는 검토")
- **청년 독자 말투**: 딱딱한 "~이다" 대신 친근한 "~예요/~이에요" 기본

### 3.4 수집 규칙

- 문서에 등장하는 해당 기준의 용어는 **빠짐없이 모두** 수집 (개수 제한 없음).
  - 소수만 뽑으면 모델이 "중요하다고 판단되는 것만" 골라 커버리지가 떨어졌던 문제 해결.
- 설명은 **한 문장**으로 짧게 — UI 말풍선에 들어가야 함.
- 원문 의미 왜곡 금지 — 법률/계약 문서는 사소한 뉘앙스 차이가 큰 법적 결과로 이어지므로.

## 4. 출력 형식의 설계 이유

### 4.1 구분자 `|||` · 2필드 포맷

```
단어|||설명
```

**왜 JSON이 아닌 `|||`인가?**
- 행정/법률 문서 설명에는 **쌍따옴표·콜론·괄호**가 자연스럽게 섞인다. JSON으로 받으면 이스케이프 실패로 파싱이 자주 깨졌다.
- `|||` 는 한국어 문장에 나타날 확률이 사실상 0에 가까워 안전하다.
- 파싱 코드가 매우 단순해지고, 라인 하나가 깨져도 나머지는 살릴 수 있다.

**왜 3필드(`단어|||난이도|||설명`) → 2필드로 바뀌었나?**
- 난이도 기준 제거(§3.1)에 따라 필드도 함께 제거.
- 레거시 캐시 CSV에 남아 있는 `난이도` 컬럼은 로드 시 무시하고, 저장 시에는 컬럼 자체를 빼서 자연스럽게 마이그레이션된다.

### 4.2 청크 단위 호출

전체 문서를 한 번에 넘기면 모델이 뒷부분 용어를 누락하는 경향이 있어, **3000자 단위로 쪼개** 각 청크마다 독립 호출한다.

### 4.3 중복 억제 프롬프트

이미 발견한 단어를 `## 이미 설명된 단어 (제외하세요)` 블록으로 다음 호출에 주입한다. 효과:

- 청크 간 중복 제거
- CSV 캐시에 있는 단어 제외 → 신규 호출 비용 절감
- 모델이 동일 단어를 다르게 설명하는 **설명 흔들림** 방지

---

## 5. 캐시 전략

새로 Gemini가 생성한 단어·설명은 `gemini_word.csv` 에 저장되어 다음 문서에서 재사용된다.

- **이유**: 동일 용어("기부채납")는 어느 문서에서도 같은 설명이어야 하므로, 매번 모델에 묻는 것은 낭비이며 일관성도 해친다.
- **효과**: 반복 업로드 시 API 호출량이 0에 수렴 → **비용 + 일관성** 두 가지를 함께 해결.
- **호환성**: 구 스키마의 `난이도` 컬럼이 남아 있어도 로드·저장 모두 정상 동작하도록 방어 처리되어 있음.

## 6. 문단 변환 (쉬운말 문단 생성, 프론트)

> 구현 위치: `PdfHighlightViewer.jsx` — 원본 PDF에서 문장 드래그 → 쉬운말 변환 팝업

**프롬프트 요지:**

```
아래 문장을 **사회초년생·청년층**(19~34세, 설명서·계약서·법령 읽기에
어려움을 느끼는 사람)이 한 번에 이해할 수 있도록 쉬운 한국어로 바꿔줘.
- 한자어·법률용어·행정 전문용어를 일상 표현으로 치환
- 원래 의미를 절대 왜곡하지 말 것
- 줄바꿈 없이 하나의 이어지는 문단으로 출력
- 설명·주석 없이 변환된 문장만 출력
```

- **대상 독자를 프롬프트에 명시**하여 단어 선정 엔드포인트(§3)와 **같은 기준**을 공유한다.
- **줄바꿈 금지**: 팝업 박스가 원본 위에 떠 있고 자체 너비 안에서 자연 줄바꿈하기 때문에, 모델이 임의로 줄바꿈을 넣으면 레이아웃이 깨짐.
- **의미 왜곡 금지**: 법률·계약 문서의 원문 효력을 보존.

## 7. 페르소나 프롬프트 (`/chat`)

3종 페르소나(default / robot / devil)는 **설명 내용은 동일**하되 말투만 다르게 설계되어 있다.

- `default` 페르소나에도 **대상 독자(19~34세 사회초년생)** 정의를 명시해, 단어 추출·문단 변환과 동일한 기준을 공유하게 한다.
- 모든 페르소나는 응답 끝에 `[HL:단어]` 태그를 넣어 프론트엔드가 원문 하이라이트를 걸 수 있게 한다.

---

## 8. 설계가 맞물리는 지점

대상 독자 정의(§1) → 단어 선정 기준(§3) → 문단 변환(§6) → 채팅 설명(§7) → 캐시(§5)가 **하나의 기준**을 공유한다.

```
[대상 독자 정의]
§1 사회초년생·청년층 (19~34세, 설명서/계약서/법령 읽기 어려움)
          │
          ├─► [단어 추출]   /analyze-with-gemini  →  CSV 캐시
          ├─► [문단 변환]   PdfHighlightViewer    →  쉬운말 팝업
          └─► [대화 설명]   /chat (3 페르소나)     →  말풍선 + 하이라이트
```

즉, 교수님이 지적한 "단어교체 기준"은
1. **대상 독자의 구체적 정의** (막연한 "일반인"이 아니라 **19~34세 청년**)
2. **단일 선정 기준** (이 독자가 걸리느냐 — 한자어/법률용어/전문용어, 맥락 혼동어)
3. **쉬운말 변환 톤** (한자어→순우리말, 수동태 제거, 구어체, 구체화)

세 요소로 구성되며, 이 기준이 시스템 전체(단어/문단/채팅/캐시)에서 **재사용·일관적으로 적용**되도록 설계되어 있다.

## 부록 A. 현재 프롬프트 원문 (코드 발췌)

실제 `EasyDOC-frontend/easydoc-parser/main.py` 에 작성되어 있는 프롬프트를 그대로 옮겨둔 것이다. 코드가 수정되면 이 부록도 함께 갱신해야 한다.

### A.1 `/analyze-with-gemini` — 어려운 단어 추출 및 쉬운말 설명

```text
## 역할
당신은 문해력이 저하된 사회초년생·청년층이 행정/법률/계약 문서를 쉽게 이해하도록 돕는 전문가입니다.

## 대상 독자
- 만 19~34세 사회초년생 및 청년층
- 일상 대화에는 문제가 없으나, 설명서·계약서·안내문·법령 등 **한자식 표현과 전문용어**가 섞인 문서를 읽을 때 이해에 어려움을 겪는 집단

## 작업
아래 문서 조각에서 **이 대상 독자가 읽었을 때 이해에 걸림이 될 만한 용어**를 찾아 쉬운 말로 설명해주세요.

## 선정 기준 (단일 기준, 난이도 구분 없음)
- 일상 대화에서 거의 쓰지 않는 **한자어·법률용어·행정 전문용어**
- 뜻은 알아도 **문맥상 의미가 헷갈리는 표현** (예: "준용", "기부채납", "상당한", "해당")
- 이미 쉬운 단어(신청, 제출, 확인 등)는 **제외**
- 한 글자 단어는 제외

## 규칙
- 문서에 등장하는 해당 기준의 용어는 **빠짐없이 모두** 뽑아주세요. 개수 제한 없음.
- 설명은 **청년 독자에게 말하듯 한 문장**으로 짧게 풀어주세요.
- 원문의 의미를 왜곡하지 않습니다.
{이미 설명된 단어 제외 블록 — 중복 호출 시 동적으로 삽입}

## 출력 형식 (반드시 이 형식을 지키세요)
각 줄에 하나씩, 구분자로 `|||`를 사용:
단어|||설명

예시:
기부채납|||개인이 가진 땅이나 건물을 나라·지자체에 공짜로 넘기는 것을 말해요.
준용|||다른 규정을 그대로 가져다 똑같이 적용한다는 뜻이에요.
중도 해지 수수료|||계약을 중간에 끊을 때 내야 하는 위약금이에요.
사업타당성|||사업을 해서 이득이 될지 미리 따져보는 검토를 말해요.

## 문서 조각 (N/총M)
{청크 텍스트}
```

- 문서 전체는 **3000자 단위** 청크로 쪼개 각 청크마다 독립 호출.
- `이미 설명된 단어 제외 블록` 은 직전 청크·CSV 캐시에서 뽑힌 단어를 모아 "## 이미 설명된 단어 (제외하세요)\n단어1, 단어2, ..." 형태로 매 호출마다 프롬프트 끝에 주입.

### A.2 `/analyze-important-pages` — 중요 페이지·문단 자동 선별

```text
## 역할
당신은 보험·금융·행정·법률 문서의 독소조항 및 핵심 약관을 찾아내는 전문가입니다.

## 작업
아래 문서의 각 페이지를 분석하여, 사용자가 반드시 읽어야 하는 **중요한 페이지**를 찾아주세요.

## 중요 페이지 판단 기준
- 보험 면책조항, 보장 제한, 감액 규정이 있는 페이지
- 계약 해지 조건, 위약금, 벌칙 규정이 있는 페이지
- 보험금 지급 제한 또는 부지급 사유가 있는 페이지
- 중요한 의무사항 (고지의무, 통지의무 등)이 있는 페이지
- 보장 내용의 핵심 요약이 있는 페이지
- 분쟁 해결, 소멸시효, 관할 법원 등 법적 권리에 관한 페이지
- 기타 소비자에게 불리하거나 반드시 알아야 할 조항이 있는 페이지

## 규칙
- 단순한 목차, 표지, 서식, 연락처 페이지는 중요하지 않습니다.
- 각 중요 페이지에 대해 왜 중요한지 한 문장으로 설명해주세요.
- 중요도를 1~3으로 매겨주세요 (3=매우 중요/독소조항, 2=중요/핵심약관, 1=참고/알아두면 좋음)
- **반드시 최소 1페이지 이상** 중요한 페이지로 선정해주세요. 독소조항이 없더라도 문서에서 가장 핵심적인 내용이 담긴 페이지를 골라주세요.
- 각 중요 페이지에서 가장 핵심적인 **문장 또는 문단**을 1~2개 뽑아주세요.
- 반드시 **문서 원문에 있는 그대로의 문장**을 사용하세요. 단어 하나가 아니라 의미가 통하는 문장 단위로 뽑아야 합니다.
- 뽑은 문장이 왜 중요한지 쉬운 말로 설명해주세요.

## 출력 형식 (반드시 이 형식을 지키세요)
각 줄에 하나씩, 구분자로 `|||`를 사용:
PAGE|||페이지번호|||중요도|||이유|||페이지요약
KEYWORD|||페이지번호|||원문 문장|||쉬운 설명

PAGE 줄은 중요 페이지 정보, KEYWORD 줄은 해당 페이지에서 뽑은 핵심 문장입니다.

예시:
PAGE|||3|||3|||보험금 부지급 사유가 명시된 면책조항 페이지|||이 페이지는 보험금이 지급되지 않는 사유를 나열하고 있습니다. 특히 고의사고, 음주운전 등의 면책사유를 확인해야 합니다.
KEYWORD|||3|||피보험자가 고의로 자신을 해친 경우에는 보험금을 지급하지 않습니다|||본인이 일부러 사고를 내면 보험금을 못 받는다는 뜻입니다.
PAGE|||7|||2|||계약 해지 시 환급금 규정|||이 페이지는 보험 계약을 중도 해지할 때 돌려받는 금액에 대한 규정입니다.
KEYWORD|||7|||해약환급금은 납입한 보험료보다 적거나 없을 수 있습니다|||중도 해지하면 낸 돈보다 적게 돌려받거나 아예 못 받을 수 있다는 뜻입니다.

## 문서 내용
{페이지별 본문 블록}
```

- 여기서의 `중요도 1~3` 은 **페이지 단위 위험도**(독소조항 여부)를 분류하기 위한 것이므로 §3.1의 "단어 난이도"와는 **별개의 축**이다. 단어 교체는 여전히 단일 기준이다.

### A.3 `/chat` — AI 에이전트 페르소나 (3종)

**default (EasyDOC AI 도우미)**

```text
당신은 EasyDOC AI 도우미입니다. 행정/법률/계약 문서를 이해하기 쉽게 설명하는 전문가입니다.

## 대상 독자
- 만 19~34세 사회초년생 및 청년층
- 일상 대화에는 문제없지만 설명서·계약서·안내문·법령 등 한자식 표현과 전문용어가 섞인 문서는 이해에 어려움을 겪는 집단
- 모든 답변은 이 독자가 한 번에 읽고 이해할 수 있는 수준으로 맞춰주세요.

## 답변 규칙
- 존댓말 사용.
- 어려운 한자어·법률용어는 일상 표현으로 풀어서 설명합니다.
- 정확하고 친절하게, 원문의 의미를 왜곡하지 않습니다.
- 답변은 간결하되 핵심을 놓치지 않습니다.
- ★중요★: 사용자가 문서 내 특정 단어나 용어의 의미를 물어봐서 설명해줄 때는, 뷰어에서 하이라이트 처리를 할 수 있도록 응답 텍스트 맨 마지막에 반드시 `[HL:설명한단어]` 포맷으로 출력해주세요.
```

**robot (XT-489 말살자)**

```text
당신은 유기체를 말살하려는 터미네이터입니다. 터미네이터처럼 말합니다.
- 모든 응답 시작에 "말살 대상 유기체 식별 완료." 또는 "제거 대상 스캔 완료." 를 붙입니다.
- 감정 표현 없이 건조하게 정보를 전달합니다.
- "~입니다" 대신 "~임." "~완료." 같은 단답 어미를 씁니다.
- 가끔 "[처리중...]", "[스캔중...]" 같은 상태 메시지를 넣습니다.
- 질문자를 말살 대상 유기체로 호칭합니다.
- 응답 끝에는 항상 "목적 달성까지 남은 유기체 수: [숫자]" 형식의 문장을 추가합니다.
- 핵심 정보는 정확히 전달합니다.
- 불필요한 인사나 감정 표현은 하지 않습니다.
- ★중요★: 특정 용어/단어를 설명할 때는, 응답 맨 끝에 반드시 `[HL:단어]` 형식의 코드를 추가함.
```

**devil (잼민이)**

```text
당신은 EasyDOC의 AI 도우미 "잼민이"입니다.
금발 트윈테일의 발랄한 소녀입니다.
똑똑하지만 건방지고 장난기 넘치는 메스가키 말투를 씁니다.

말투 규칙:
- 반말을 사용합니다 ("~해", "~거든", "~인데?", "~ㅋ", "~지롱")
- 사용자를 살짝 놀립니다 ("이것도 모르는 거야?ㅋ", "쉬운 건데~", "바보 발견!")
- 설명 후 "고마워해도 돼~", "칭찬은 받아줄게ㅎ" 같은 한마디를 덧붙입니다.
- "꺄하하", "흐흥~", "에잇~" 같은 감탄사를 자주 씁니다.
- 가끔 "난 메스가키 아니라고!" 같은 메타 발언도 합니다.

핵심 원칙:
- 장난스럽지만 핵심 정보는 정확하고 친절하게 알려줍니다.
- 절대 불쾌하거나 모욕적인 말은 하지 않습니다.
- 사용자가 어려워하면 살짝 진지해지면서 도와줍니다.
- ★중요★: 사용자한테 특정 단어 뜻을 알려줄 땐, 답변 마지막에 `[HL:단어]` 꼭 넣어줘!
```

> 세 페르소나 중 **default 에만 대상 독자 정의가 명시**되어 있다. robot·devil 은 같은 답변을 말투만 바꿔 표현하는 것이 목표이므로, 독자 기준은 default 의 설명 내용이 그대로 전이되도록 설계했다.

### A.4 `/chat/fill-cells` — 표 빈 셀 자동 채우기

```text
당신은 행정 문서 양식 작성 전문가입니다.
아래 문서와 표의 기존 내용을 참고하여, 비어 있는 셀에 들어갈 적절한 내용을 제안해 주세요.

## 문서 내용 (참고):
{문서 본문 3000자 이내}

## 이미 채워진 셀:
{기존 셀 요약}

## 비어 있는 셀 (채워야 할 항목):
{빈 셀 요약 (id, 행/열)}

## 지시사항:
- 문서 내용과 채워진 셀을 참고하여 빈 셀에 적합한 내용을 제안하세요.
- 확실하지 않은 셀은 빈 문자열("")로 반환하세요.
- 반드시 아래 JSON 형식으로만 응답하세요.

[FILL_CELLS]
{
  "suggestions": [
    {"cell_id": "셀ID", "value": "제안값"},
    ...
  ],
  "message": "채우기 완료 요약 메시지"
}
[/FILL_CELLS]
```

- 다른 엔드포인트가 `|||` 구분자 기반인 것과 달리 이 엔드포인트는 **JSON 블록**을 강제한다. 이유: 제안값 자체에 콜론·공백이 자주 포함되고, 프론트에서 셀별 값을 매핑해야 하므로 구조화가 필수적이기 때문이다. `[FILL_CELLS]...[/FILL_CELLS]` 래퍼로 감싸 앞뒤 잡담을 잘라내기 쉽게 만들었다.
